## 2. Архитектура и управление схемой БД

Создание и изменение схемы базы данных выполняется **строго через SQL-миграции Flyway**.
Автоматическое создание или изменение схемы через Hibernate отключено:
```properties
spring.jpa.hibernate.ddl-auto=validate
spring.flyway.enabled=true
spring.flyway.locations=classpath:db/migration
```

### Версии схемы (Flyway):
1. **`V1__create_tables.sql`** — создание базовых таблиц `pets` и `appointments`:
   - Первичные ключи на основе `UUID` (`gen_random_uuid()`).
   - Внешний ключ: `pet_id UUID NOT NULL REFERENCES pets(id)`.
2. **`V2__add_notes_to_appointments.sql`** — содержательная эволюция схемы:
   - Добавление колонки заметок врача: `ALTER TABLE appointments ADD COLUMN notes TEXT;`.
   - Существующие данные сохраняются в полном объёме.

## 3. Выполнение требований лабораторной работы

### 1. Персистентность данных
Все данные сохраняются в реляционной СУБД PostgreSQL 18. После перезапуска приложения данные остаются на месте (проверено вручную и через тесты).

### 2. Связи между ресурсами и целостность 
* Сущности `Pet` и `Appointment` связаны отношением `@ManyToOne(fetch = FetchType.LAZY)`.
* Внешний ключ `FOREIGN KEY (pet_id) REFERENCES pets(id)` на уровне БД защищает от создания записей к несуществующим питомцам.
* Запрещено удалять питомца, если у него есть активные приёмы (`SCHEDULED`) — возвращается `409 Conflict`.
* При удалении питомца с завершёнными/отменёнными приёмами они каскадно очищаются, предотвращая появление висячих ссылок.

### 3. Атомарная транзакция над связанными объектами 
* Реализована операция смены владельца питомца: `POST /pets/{id}/transfer`.
* В рамках единой транзакции (`@Transactional`):
  1. Обновляется имя владельца питомца (`Pet.ownerName`).
  2. Все активные приёмы питомца (`SCHEDULED`) отменяются со статусом `CANCELLED` и комментарием о смене владельца.
* При возникновении ошибки (например, при передаче `trigger-error` или ошибке валидации) происходит полный откат транзакции (**Rollback**): ни владелец, ни статусы приёмов не изменяются. Поведение покрыто тестом `shouldRollbackAllChangesWhenErrorOccursInTransaction`.

### 4. Эволюция схемы базы данных
* В проекте присутствуют две последовательные миграции Flyway (`V1` и `V2`).
* Новая установка накатывает обе миграции последовательно; существующая установка сохраняет накопленные данные.

### 5. Решение проблемы N+1 
* Для получения списка приёмов с полной информацией о связанных питомцах реализован метод:
  ```java
  @Query("SELECT a FROM Appointment a JOIN FETCH a.pet")
  List<Appointment> findAllWithPet();
  ```
  и эндпоинт `GET /appointments/detailed`.
* Независимо от количества элементов в списке (10, 30 или 100), выполняется **ровно 1 SQL-запрос** с `JOIN FETCH`, предотвращая N дополнительных запросов. Поведение проверено тестом `shouldFetchListWithRelatedEntitiesEfficiently` на выборке из десятков объектов.

### 6. Тестирование 
* **Юнит-тесты бизнес-логики (49 тестов):** выполняются **без запуска Spring-контекста** за ~0.1 секунды (чистые POJO-тесты с in-memory репозиториями).
* **Интеграционные тесты БД (3 теста):** проверяют персистентность связей, корректный откат транзакций при сбоях, а также отсутствие проблемы N+1.

## 4. Инструкция по запуску

### Шаг 1. Запуск PostgreSQL в Docker
```bash
docker compose up -d
```
БД доступна на `localhost:5433` (пользователь `pet_clinic`, пароль `pet_clinic`, база `pet_clinic`).

### Шаг 2. Запуск приложения
```bash
mvn spring-boot:run
```
Приложение запускается на порту `8080`. При старте Flyway автоматически накатывает миграции `V1` и `V2`.

### Шаг 3. Запуск тестов
```bash
mvn test
```
Все 52 теста (49 юнит + 3 интеграционных) проходят успешно.

### Шаг 4. Прогон сценариев через curl-скрипт
```bash
bash requests.sh
```
Скрипт проверяет все сценарии, валидации, откат транзакции и детальную выборку без N+1.
